# 性能记录

## 2026-10-01：精确索敌与模拟步耗时

本轮保留每步索敌频率、战斗规则、原桶量化和 `1e-9` 同距按 ID 决胜规则。局部查询先与敌队实际占用的桶范围求交，避免扫描空地；远场查询按 `alive` 原顺序分成 16 人组，以距离下界排除不可能胜出的整组。没有重排候选，也没有缓存上一帧目标。

远场位置裁剪只在战斗核的 `planningStep` 阶段启用，此时普通单位先记录运动计划，随后统一位移。含驻军的组始终读取实际位置，覆盖“规划开始时定时攻塔毁塔、驻军立即出塔”这一例外。非规划查询继续使用原来的实时扫描；每次空间索引重建都会更新分组及边界。

### 可复现方法

```sh
node tools/perf-benchmark.mjs > /tmp/battle-perf.json
node --test tests/targeting-nearest.test.js tests/targeting-determinism.test.js tests/lockstep.test.js tests/camps-lockstep.test.js
```

基准使用真实 `stepBattle(1/60)`、部署、导航、经济和营队逻辑，Phaser 绘制由现有 headless harness 替代。双方兵力相等，每方 50% 剑士、20% 枪兵、20% 弓手、10% 骑兵。平地为普通混兵对战；山河使用真实 `territory` 地形和领土模式，双方自动征兵关闭，防止兵数改变。

每个配置预热 20 步，平地测 120 步、山河测 30 步，分别重复 3 次，并交替先运行优化前或优化后。表中均值和 P95 为三次测量各自的中位数。可通过 `--warmup=20 --steps=120 --territory-steps=30 --repeats=3` 调整。耗时没有硬编码测试阈值；JSON 同时输出每次均值、P95、最长步耗时、状态哈希和环境信息。测量时避免同时运行全量测试或浏览器压测。

优化前使用冻结于 `0c7a781` 的空间索引；该索引不提供新查询方法，因此调用原有索敌路径。逐目标验证另外使用冻结的完整旧索敌函数作为 oracle，两者保存在 `tests/targeting-reference.js`。

### 行为一致性

五组配置的优化前后预热与结束状态哈希全部一致。山河额外使用 `net/lockstep.js` 的正式 `battleProjection` / `hashProjection`：200 人结束哈希 `1rq0rue`，440 人 `1ip883d`。普通模式不满足该官方投影的领土前置条件，改用单位全部基础字段、目标 ID、箭矢和战报的精确 JSON 指纹，仅排除生成时随机的渲染字段 `bobPhase` / `slideOff`；平地 200/500/1000 人结束哈希分别为 `ybv9nn` / `15lyqmq` / `1kemaxl`。

回归覆盖固定种子随机地图与三阵营、量化桶边界、同距及容差链、溃逃敌军、驻军/车辆/死亡/撤离过滤、毁塔出塔、非规划移动、反复缩短与重建索引；另用真实混兵交战 900 步逐步比较精确状态，确保发生攻击与伤亡，并用真实山河运行 180 步逐步比较官方联机投影。原有双端命令泵与营寨锁步回归也通过。

## 2026-10-02：据点特色与民夫自卫的边际成本

本轮在模拟热路径上新增了三处查询：渡口浅滩系数（单位行军）、高地士气系数（每步士气结算）、
林口施工速度（每帧建筑循环）。测量条件与 2026-10-01 相同：Apple M4 / Node v22.23.2，
山河领土地形、双方各 144 人（100 剑士 / 40 弓手 / 4 民夫），自动征兵关闭，
`stepBattle(1/60)` 预热后取 300 步 × 5 轮的最优均值；微基准为单进程 20 万次调用。

| 查询 | 单次成本 | 说明 |
| --- | ---: | --- |
| `shallowSpeedFor(scene, team)`（冷路径） | 144 ns | 只有踩在浅滩上才会走到 |
| `shallowSpeedFor(...)`（热路径优化后） | 平地/林地不调用 | 先按地形默认系数取一次，等于默认浅滩值才查归属 |
| `moraleLossScale(scene, unit)`（领土） | 47.5 ns | 每单位每步一次，约 281 人 × 48ns ≈ 14 µs/步 |
| `moraleLossScale(...)`（非领土模式） | 17.3 ns | 直接短路，且不再惰性创建派生缓存 |
| `buildSpeedScale(scene, building)` | 15.5 ns | 每帧每座未完工建筑一次 |
| `stepBattle` 单步（281 人在场） | 5.81 ms | 与上一轮同量级，未观察到回退 |
| 营寨渲染帧（22 座完工塔 / 328 单位） | 0.07 ms/帧 | 独立复核曾测得逐塔回查模拟为 0.18 ms/帧；改为每帧一次预约扫描后降到 0.03–0.07 ms |

同一时间段内的正式基准 `node tools/perf-benchmark.mjs`（预热 20 步、平地 120 步 / 山河 30 步、
各重复 3 次、退出码 0）五组配置 `sameHashes=True`：平地 200/500/1000 人为 1.82 / 2.09 / 2.57 倍，
山河 200/440 人为 1.24 / 1.46 倍（前=冻结于 `0c7a781` 的旧索敌路径）。基准的"前/后"衡量的是
上一轮索敌优化，本轮只确认它未被拖慢、且哈希仍然一致；耗时不设硬阈值。

## 2026-10-02 review-fixes：第一轮定点修复前后的 A/B 对比（比较对象声明）

本节比较对象是**第一轮 6 项 P2 定点修复之前（A）与之后（B）的完整工作树**：
A = 修复前工作树的完整快照（含上一轮索敌优化与玩法增强的全部未提交改动，存于
`abs-review-baseline/A`，同机同 Node 运行），B = 修复后工作树。两轮跑同一份脚本
（`tools/review-perf-sim.mjs` / `tools/review-perf-browser.mjs`）与同一初始兵力；
两个场景并不完全相同，分别描述如下。

- **模拟场景**（`review-perf-sim.mjs`）：领土 260×180，双方 AI 自动征兵 + 自动建设 +
  自动驻塔，中央 120 名自由单位两军对垒持续交战，测量期**每秒双方各补 1 名步兵**。
  A/B 完全同构；warm 窗口伤害 ≈3400、接敌 <1 秒、施工中 4–5 座、驻塔 4 人，
  证明交战/施工/驻塔/征兵都在真实发生。
- **浏览器场景**（`review-perf-browser.mjs`）：同地图与 AI 设置，中央 120 名自由单位
  **一次性**对垒，**没有模拟脚本的每秒补兵**；渲染帧与游戏主循环全开。

结果（全部原始样本保留在 `.omc/evidence/review-perf/`，不筛掉任何不利轮次）：

- 模拟步（`stepBattle(1/60)`，A/B 交替各 5 轮 × 30 秒，中位数）：
  A mean 16.65ms / p95 23.51ms；B mean 16.38ms / p95 23.18ms。两侧终局兵力同为 346。
- 桌面浏览器帧（Chromium 有头窗口 1440×1000，预热 8 秒后 20 秒窗口，ABBA×2 交替；
  FrameStats 全窗口统计）：A 平均 fps 43.1 / 长帧(>50ms)合计 192；
  B 平均 fps 46.3 / 长帧合计 144。相邻样本差异极大（如 A-run4 59.9fps/长帧 0
  与 B-run3 28.9fps/长帧 92 互为近邻），测量期间本机 load average ≈5.5–7.2。

**结论（按证据强度如实表述）**：模拟基准总体指标接近；浏览器样本总体均值偏向 B，
但环境噪声较大（相邻样本摆动远超 A/B 差异），尚不能可靠判断浏览器性能差异。
此前"成对不劣/浏览器无回退已证明"属过强表述，已撤回。该结论只覆盖 A↔B。

## 渲染、加载与操作

- 地图从一次性完整烘焙改为合作式分帧任务，纹理块由 1024px 改为 512px，镜头附近优先。任务使用 8ms 软预算：只能在工作段之间让出主线程，单块 Canvas 绘制或 GPU 上传仍可能超过预算。加载时显示进度并推迟开战倒计时；更换地图取消旧任务。首页缩略图绘制后恢复原棋盘尺寸，避免污染后台地图任务。
- 离屏单位隐藏并暂停 Sprite 动画，回场按当前状态恢复；仍正常参加战斗。箭矢命中按原模拟步推进，显示帧只画一次箭，离屏箭照常命中。尘土复用一个 Graphics 和最多 96 条记录；静态旗圈几何缓存，远景仅显示最多 24 个己方营标记。
- 征兵长按按批次刷新界面，预算不足或队列满即停止；建设面板关闭时不遍历重建，单兵文字最多每 125ms 刷新。回归中的 195 次购买只产生 31 次 HUD 刷新（初次加 30 轮长按）。这些计数是固定测试场景，不是浏览器整帧测量。
- 联机驻守/集结点击立即给出目标圈和已接收提示。LOOKAHEAD 和命令顺序保持不变，没有用压缩同步缓冲掩盖延迟。

## 如何区分卡顿

右上角性能读数的悬浮提示保留最近最多 240 帧。帧间隔采用 Phaser 的 `rawDelta`，避免其平滑算法隐藏尖峰；P95、最慢帧与超过 50ms 的次数反映整帧间隔。主循环/模拟耗时来自 `performance.now()`，不包括随后 GPU 绘制；它们与帧间隔含义不同。

联机显示「同步等待」时，提示中提供等待累计时长、最长连续等待和连续可执行步数。缓冲只计算从当前回合起双方包齐全的连续区间，未来零散包不能掩盖缺包。FPS 低优先检查渲染和模拟；FPS 正常而持续同步等待，应排查两端性能、浏览器后台节流及网络。此诊断不改变模拟推进策略。
